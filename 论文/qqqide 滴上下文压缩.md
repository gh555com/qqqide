## §1 铁律

```
┌──────────────────────────────────────────────────────────────┐
│  🔴 压缩 = 背包重构。成功前不写盘，失败原子回滚。            │
│  🔴 客户端做"可逆机械筛"（消息→压缩原料x），AI 做"不可逆    │
│     语义提纯"（原料x→压缩饼干）。职责不交叉。                │
│  🔴 压缩饼干落盘只存一次。多轮压缩产生新饼干→替换旧饼干，    │
│     不叠加。                                                 │
└──────────────────────────────────────────────────────────────┘
```

## §2 基础定义

### 背包
AI 对话的完整上下文。即 `agent.conversation[]` 数组。每条消息含 `{role, content, tool_calls?, tool_call_id?, _floor}`。

**命名冲突**：避免和 UI 上的"上下文背包"（goods/conv/）混淆。本文使用**背包**专指 API 消息数组。

### Z（注入物）
背包中每次请求都会携带但**不是对话内容**的消息集合，压缩时必须剥离：

| 条目 | 来源 | 说明 |
|------|------|------|
| msg[0] | `_refreshRules()` | Vision context + global/project rules + reminder |
| toolsdef | `getTools()` | 15 个工具定义，~4K chars，body 顶层字段 |
| guard | Go 服务端注入 | system-prompt.txt，14964 chars |
| CURRENT TIME | `getTimeContext()` | 每条 user 消息末尾的时间戳 |
| `_system` 恢复消息 | `_attemptRecoverySend` | 系统注入的错误历史 |
| 压缩元信息 | 压缩成功/失败消息 | "压缩失败: 已回滚"等 |

Z 在压缩请求的 API 调用中**也不发送**——压缩只关心对话内容，不需要工具定义/规则/时间戳。

### D（全量）
从上次压缩结束至今，背包中**所有尚未被压缩的原始消息**。是一个纯数量概念：

```
D = |W6| + |比 W6 更新的所有消息|
```

每次压缩成功后，D 重新从 W6 开始计数。

### 压缩原料 X（原料）
D 中落在断点之前的消息。是被送入"机械筛"的那部分。

```
X = D - 断点
```

性质：原始 OpenAI messages 格式的对话历史，但已剥离 Z。

### 断点（切分指针）
一个整数消息索引，标定"保留"和"压缩"的分界线。断点之后的消息保留为 W6（原始），断点之前的消息成为 X（原料）。

**计算规则**：
1. 从最后一条消息往回数，先找到最近 6 层楼的完整消息 → 得到条数 N，此为起始锚点
2. 对锚点内消息称重（`_estimateMsgTokens`，content + tool_calls JSON / 2.5）
3. 若总重 <（背包总 token × 10%），向前扩展（每次加 1 条消息，称重），直到满足 10% 阈值
4. 阈值后的消息索引 = 断点

**保证**：W6（断点后）≥ 10% 总 token 重量，且至少 4 层完整楼层。

### W6（热消息）
断点之后保留不压的原始消息。W6 保持 OpenAI messages 格式原样留在 conversation 中。

**命名由来**：最初定义为"最近 6 层楼"，但实际数量由 10% token 阈值动态决定。

### 压缩饼干（饼）
原料 X 经"机械筛"加工后，再经 AI（tier 4）语义提纯产生的最终产物。包含：

- **narrative**：跨楼层的叙事弧线（纯文本，8K+ chars）
- **facts**：结构化事实列表（每行 `类型:XX | 内容:YY | 关键词:ZZ`，≥25 条）
- **archives**：每层楼一句话摘要（每行 `第N层: ...`）

压缩饼干落盘后，**X 中的原始消息从 conversation 中 splice 移除**。饼 + Z + W6 构成新背包。

## §3 压缩流水线

```
┌─────────────────────────────────────────────────────────┐
│ 背包：全量消息 [msg0 | ...360条原始... | ...240条热...]  │
│ D = 600                                                  │
│ 1. 剥离 Z                                               │
│ 2. 计算断点 = 360                                       │
│ 3. X = D - 断点 = 360 条                                │
│ 4. 机械筛：X → 12K chars 压缩原料（方案三楼层摘要式）   │
│ 5. AI 语义提纯：12K chars → 压缩饼干（narrative+facts+archives）│
│ 6. splice conversation：移除 X 原始消息，注入压缩饼干   │
│ 7. 新 D = 240（W6 起点）                                │
└─────────────────────────────────────────────────────────┘
```

## §4 机械筛（方案三：楼层摘要式）

**职责**：客户端将原始消息 X 转换为 AI 可直接消费的纯文本。零 AI 参与，100% 确定性。

### 转换规则

| 原始消息 | 压缩原料格式 |
|---------|------------|
| user，有 content | `Q: [content]` |
| assistant，仅 content | `A: [content]` |
| assistant，仅 tool_calls | `[A → tool_name] file1, file2 ✓` |
| assistant，content + tool_calls | 先 `A: [content]`，再 `[A → tool_name] ...` |
| tool 返回 | 合并到上一行的 ✓/✗ 摘要中 |

### 工具返回摘要规则

| 工具 | 返回摘要 |
|------|---------|
| read_file | `✓ L:N/M`（行范围） |
| edit_file | `✓ N处` |
| edit_file 失败 | `✗ [原因]` |
| write_file / create_file | `✓ 已写入` |
| run_command | `✓` 或 `✗ exit N` |
| get_diagnostics | `✓ OK` 或 `✗ N errors` |
| search_text / search_content | `✓ N处匹配` |
| list_files / find_files | `✓ N项` |

### 产出格式

```
=== F17 ===
Q: 还是失败了，看看有没有日志
[A → read_file] f16/all.json ✓ L:80/80
A: 找到两个新bug。Bug1: auto-save在半路写盘污染_ctx。
   已修复：加_compressing检查。
[A → edit_file] panel-clock.js, panel-quest-ui.js, agent-context.js ✓ 3处
A: Ctrl+R后生效。

=== F18 ===
Q: 上下文压缩还是失败！查f19 f20
[A → read_file] f14/all.json, f15/all.json ✓ 2 files
A: 诊断：facts raw=70c，cached_tokens=100864→99.9%缓存命中→
   返回旧垃圾。V3架构把110K塞进1个user content，根因在此。
A: 需要从零设计原料拼装。写完整plan。
```

## §5 AI 语义提纯（不可逆）

**职责**：从压缩原料中提取叙事弧线、结构化事实、楼层摘要。三个专家并行，tier 4。

### 输入

压缩原料（~12K-18K chars 纯文本）+ 简短指令。

### 输出期望

| 专家 | 产出 | 期望 |
|------|------|------|
| Narrative | 跨楼层叙事弧线 | 8K+ chars，每层 2000-4000 字 |
| Facts | 结构化事实 | ≥25 条，`类型:XX | 内容:YY | 关键词:ZZ` |
| Archive | 楼层摘要 | 每层一句话，`第N层: ...` |

### 与之前版本的本质区别

```
旧架构：308K tokens → AI 同时处理 "读格式" + "读内容" + "写格式"
新架构：12K chars  → AI 只做"读内容 → 写叙事"（格式已被机械筛解决）
```
