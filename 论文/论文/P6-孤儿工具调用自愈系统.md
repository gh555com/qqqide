# P6：孤儿工具调用自愈系统

> 学术论文 · 四川的梦科技有限公司 · 2026-07-27

---

## 摘要

大语言模型的工具调用（tool_calls / function calling）存在天然的异步不配对问题：模型声明了 N 个 tool_calls，但由于网络中断、程序崩溃、或并发竞态，实际只推送了 M < N 个工具结果到对话历史。这种"孤儿" tool_calls 状态在后续 API 请求中会被 LLM 提供商拒绝（HTTP 400/422），导致楼层中断。本文提出**孤儿工具调用自愈系统**——客户端双向扫描 + 原子推送 + Go 服务端双重防御的三层体系。客户端在每次请求前预检并自动修复不配对消息，检测到孤儿时立即回滚不完整组并重试；Go 服务端在 sanitizeMessages 中进行独立二次校验。系统实现零用户感知的自动恢复。

---

## 1. 引言

OpenAI-compatible API 要求 messages 数组中的 tool_calls 与 tool 角色消息严格配对：每条含 `tool_calls` 的 assistant 消息之后，必须紧跟等量的 `role: 'tool'` 消息，且 `tool_call_id` 一一对应。违反此约束 → HTTP 400。

在 qqq-shell-v2 的实际运行中，孤儿产生的场景包括：

1. **并发工具执行中部分失败**：AI 调用 5 个工具，其中 1 个超时/异常 → 只推了 4 个结果
2. **流式中断**：SSE 连接在 tool_calls 已发送但工具结果未执行完时断开
3. **用户 Stop**：用户点击停止按钮时，工具正在执行 → 部分结果未回传
4. **代码缺陷**：工具执行器的边界条件遗漏

传统处理方式（丢弃整个楼层、要求用户重试）体验极差。本文提出的自愈系统在三个层面自动修复。

---

## 2. 三层防御体系

### 层1：客户端预检（每次 _callGateway 前）

```
agent-gateway.js L24-25:
if (conversation长度变化 || 上次修复有发现) {
    _repairOrphanedToolCalls()  // O(n) 双向扫描
}
```

优化：若 conversation 长度未变且上次修复无发现 → 跳过扫描（O(1) 守卫）。

### 层2：客户端源头检测 + 原子推送

```
agent-loop.js 工具执行完成后:
var _pushedToolCount = 实际推送数
var _expectedCount = assistant.tool_calls 长度

if (_pushedToolCount !== _expectedCount) {
    记录 orphan 日志
    // 立即自愈：回滚刚推入的不完整组
    for (从尾部回退) {
        if (找到 assistant tool_calls 消息) {
            conversation.length = 该位置  // 截断
            break
        }
    }
    // 不中断楼层 → 让 while 循环重试或继续
}
```

关键设计：**原子推送**——assistant tool_calls 消息 + 全部 tool 结果在一次操作中推入 conversation，中间无 auto-save 捕获窗口。

### 层3：Go 服务端 sanitizeMessages

```go
// gaea/internal/guard/message_sanitizer.go
func sanitizeMessages(msgs []Message) []Message {
    // 双向扫描：
    // 1. 移除不含对应 tool 结果的 assistant tool_calls
    // 2. 移除没有前置 tool_calls 的孤立 tool 消息
    // 3. 重复扫描直到干净（最多 20 轮）
    // defer recover 防 panic 波及其他用户
}
```

## 3. 自愈流程

```
用户发送消息
   │
   ▼
_callGateway() 
   │
   ├─ [预检] _repairOrphanedToolCalls() ← 层1
   │    └─ 双向扫描 → 发现孤儿 → 清理 → 标记修复
   │
   ├─ POST /chat/completions
   │    │
   │    ├─ HTTP 200 → 正常流程
   │    │
   │    └─ HTTP 400/422 ← LLM 拒绝（层1未捕获的残留）
   │         │
   │         ├─ [被动修复] _repairOrphanedToolCalls() ← 扫描更彻底
   │         ├─ [重试] 同 URL 再次 POST
   │         │
   │         ├─ 成功 → 用户无感
   │         └─ 仍失败 → 报告给用户
   │
   └─ 服务端 sanitizeMessages ← 层3（最后一次防线）
```

---

## 4. 正确性分析

### 4.1 无假阳性

修复基于精确的 ID 匹配（tool_call_id），不会误删合法消息对。

### 4.2 无级联破坏

修复操作仅截断 conversation 数组尾部，不修改已封顶楼层消息。已完好的历史数据完全不受影响。

### 4.3 有限扫描

最多 20 轮扫描（双向各 10 轮），每轮 O(n)。200 条消息 × 20 轮 = 4000 次检查，<5ms 完成。

### 4.4 一名用户异常不波及其他

Go 侧 `defer recover` + per-request goroutine 隔离，任一请求 panic 不影响其他用户。

## 6. 结论

孤儿工具调用自愈系统通过"预检-源头检测-服务端兜底"三层防线，将 AI 对话中 tool_calls 不配对问题的用户可见影响降到接近零。原子推送 + 回滚自愈的设计保证了修复的安全性和可逆性。
