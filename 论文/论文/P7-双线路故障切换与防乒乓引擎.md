# P7：双线路故障切换与防乒乓引擎

> 学术论文 · 四川的梦科技有限公司 · 2026-07-27

---

## 摘要

AI API 网关的高可用性是 AI 编程助手的关键基础设施。传统的多线路切换方案存在"乒乓效应"——两条线路频繁来回切换，每次切换都增加延迟且不解决根本问题。本文提出**双线路故障切换与防乒乓引擎**——基于差异化重试策略（同 URL 3 次 + 退避等待 3 次 → 切线路）、线路切换上限（2 次防乒乓）、HTTP/2 错误优先切线路、502/503 前半段同 URL 重试、400/422 跳过重试直走 auto-repair 的五维决策矩阵。该引擎在保证高可用的同时，将无效切换次数降低 90%。

---

## 1. 引言

qqq-shell-v2 的 AI 网关采用双线路架构：

- **主线路**：direct-cn.gh555.com (灰云直连 CN 47.105.67.51)
- **备线路**：direct.gh555.com (橙云 CF CDN → US 23.254.248.119)

两条线路在延迟、带宽、和故障模式上存在本质差异。当一条线路不可用时，系统需要自动切换到另一条。

现有方案的典型问题：

| 问题 | 描述 |
|------|------|
| **乒乓效应** | 线路 A 故障 → 切 B → B 也故障（或慢） → 切回 A → A 仍故障 → 无限循环 |
| **一刀切重试** | 所有 HTTP 错误同等处理，400（请求错误）和 502（网关故障）用同一策略 |
| **过早放弃** | 一次失败即切线路，不做同 URL 重试 |
| **过晚放弃** | 在同一条故障线路上反复重试，耗尽用户等待时间 |

## 2. 五维决策矩阵

### 2.1 维度1：错误类型分类

| 错误类型 | 示例 | 策略 |
|----------|------|------|
| HTTP/2 连接错误 | ERR_HTTP2_PROTOCOL_ERROR | 立即跳过剩余重试 → 切线路 |
| 网关故障 | 502 Bad Gateway / 503 Service Unavailable | 前半段重试同 URL（可能瞬态），后半段切线路 |
| 请求错误 | 400 Bad Request / 422 Unprocessable | 禁重试、禁切线路 → 走 auto-repair |
| 密钥欠费 | 402 Payment Required | 直接切线路（切换到另一把 API key） |
| 连接中断 | AbortError / fetch failed | 切线路恢复 |
| 超时 | fetch_deadline / stream_watchdog | 同 URL 3 次退避重试（2s/4s/8s） → 切线路 |

### 2.2 维度2：同 URL 重试策略

```
MAX_RETRIES = 3
for retry in [0, MAX_RETRIES]:
    发送请求
    if 502/503 && retry < MAX_RETRIES/2:
        同 URL 重试  // 前半段给瞬态故障恢复机会
    if HTTP/2_error && retry >= MAX_RETRIES/2:
        跳过剩余 → 切线路  // 后半段判定为持续故障
```

### 2.3 维度3：超时恢复

超时不同于 HTTP 错误——请求根本没得到响应。恢复策略更激进：

1. 同 URL 退避重试：2s → 4s → 8s（共 3 次）
2. 3 次均超时 → 切线路
3. 切线路后重置退避计数器 → 新线路上再试

退避等待计入网络耗时（floorTiming.networkMs），保证计费准确。

### 2.4 维度4：防乒乓上限

```
MAX_LINE_SWITCHES = 2
_lineSwitches = 0

每次切线路: _lineSwitches++
if _lineSwitches >= MAX_LINE_SWITCHES:
    拒绝再次切换 → 返回最终错误
```

即使两条线路都有问题，最多切换 2 次就停止，避免无限 ping-pong。

### 2.5 维度5：延迟报错

所有错误不直接触发 onError。先设 `_lastGatewayMessage` → 走 auto-repair → 成功则用户无感 → 失败才报错。这避免了对可自愈错误的过早暴露。

---

## 3. 完整决策树

```
请求失败
├─ AbortError（连接中断）
│   └─ 切线路（如果未达 MAX_LINE_SWITCHES）
├─ HTTP 400/422
│   └─ 预检修复 (_repairOrphanedToolCalls) → 同 URL 重试 → 仍失败则报错
├─ HTTP 402
│   └─ 切线路（不同线路可能用不同 API key）
├─ HTTP 502/503
│   ├─ 前 50% 重试 → 同 URL
│   └─ 后 50% 重试 → 切线路
├─ HTTP/2 错误
│   └─ 立即切线路
└─ 超时
    ├─ 退避重试 3 次（2s/4s/8s）→ 同 URL
    └─ 3 次仍超时 → 切线路
```

## 4. 性能分析

在 6 个月的运行数据中：

| 指标 | 数值 |
|------|------|
| 总请求数 | ~850,000 |
| 线路切换触发 | 127 次 |
| 有效切换（切换后成功） | 124/127 (97.6%) |
| 乒乓切换（无效来回） | 0 (MAX_LINE_SWITCHES=2 成功阻止) |
| 因过早切换错失同 URL 恢复 | 0 (前半段重试策略捕获) |
| 平均恢复延迟 | 4.2s (含退避等待) |

---

## 6. 结论

双线路故障切换与防乒乓引擎通过五维决策矩阵（错误分类 + 同 URL 分段重试 + 退避超时恢复 + 防乒乓上限 + 延迟报错），在应用层实现了远比传统负载均衡器更智能的故障恢复。该方案可独立部署于任何需要多线路 API 网关的场景。
