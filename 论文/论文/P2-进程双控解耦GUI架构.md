# P2：进程双控解耦的图形用户界面装置

> 学术论文 · 四川的梦科技有限公司 · 2026-07-27

---

## 摘要

后台服务进程的 GUI 管理存在两个天然正交的维度：进程运行状态（存活/停止）与自动重启策略（开启/关闭）。现有方案将二者耦合在单一开关中，导致用户意图歧义和状态表示错误。本文提出**进程双控解耦 GUI 架构**——将进程状态指示器（gpDot ●）与自启动开关（Toggle）完全分离为两个独立控件。gpDot 以四态颜色（绿/灰/黄/橙）百分百反映进程实际存活状态（基于 PID 文件 + 5s poll + push 双轨检测），Toggle 仅控制 watchdog 自启动行为。二者各自独立操作：用户可手动启停进程而不影响自启动策略，可关闭自启动而不杀进程。该架构已在 qqq-shell-v2 IDE 的多个后台 goods 进程中部署，根治了传统单开关方案的状态歧义问题。

---

## 1. 引言

集成开发环境（IDE）中运行着多种后台服务进程：AI 模型网关、文件监听器、语法检查器、搜索索引等。用户对这些进程的管理需求可分为两个独立维度：

- **状态维度**：进程当前是否存活？
- **策略维度**：进程崩溃后是否应自动重启？

传统 GUI 设计将二者合并为一个 toggle 开关：开启 → 启动进程 + 注册 watchdog；关闭 → 杀进程 + 注销 watchdog。这种耦合设计导致以下问题：

1. **意图歧义**：用户关闭 toggle 是"暂时不想用"还是"永久关闭"？系统无法区分。
2. **手动操作无法表达**：用户通过终端手动启动进程后，GUI 无法正确反映"进程在运行但自启动策略未开启"。
3. **中间态不可见**：进程崩溃后 watchdog 正在恢复中，用户看不到这一过渡状态。

本文提出的双控解耦架构彻底分离这两个维度。

## 2. 系统设计

### 2.1 双控件模型

| 控件 | 类型 | 语义 | 操作 |
|------|------|------|------|
| **gpDot (●)** | 圆形状态指示灯 + 手动按钮 | 进程当前存活状态 | 点击：绿→优雅退出 / 灰→手动启动一次（不注册 watchdog） |
| **Toggle** | 开关 | 自启动策略 | ON→启动进程+watchdog / OFF→仅停 watchdog 不杀进程 |

### 2.2 四态颜色状态机

```
     ┌──────────────────────────────────────┐
     │  ●灰 + Toggle灰  →  进程已停止，无自启动  │
     │  ●绿 + Toggle绿  →  进程运行中，有自启动  │
     │  ●绿 + Toggle灰  →  进程运行中（手动启动）│
     │  ●灰 + Toggle绿  →  进程崩溃，watchdog恢复中│
     └──────────────────────────────────────┘
```

gpDot 颜色百分百反映进程 PID 实际存活状态，通过双重检测保证：

- **快速通道（push）**：进程退出事件 → IPC 推送 → 即时更新
- **慢速通道（poll）**：5 秒间隔轮询 PID 文件 → 兜底检测

### 2.3 跨窗口单例检测

对于禁止多开的 goods（allowMultiple=false），系统使用 PID 文件锁：

1. 启动前：读取 `Data/alphal/goods/{goodsId}.pid` → 检测 PID 是否存活 → 存活则拒绝启动
2. 启动后：写入当前 PID → 进程退出时清理
3. 跨窗口：所有 Electron 窗口共享同一 PID 文件目录 → 天然互斥

### 2.4 Watchdog 自愈

Toggle=ON 时，watchdog 每 5 秒检测进程存活。若进程崩溃：

1. ● 变灰（表示进程已死）
2. watchdog 自动重启进程
3. 进程启动成功 → ● 变绿
4. 若 3 次重启失败 → ● 保持灰 + qoast 告警

## 3. 与现有方案对比

| 特性 | 单开关方案 | systemd units | Docker restart policy | 本方案 |
|------|-----------|--------------|----------------------|--------|
| 状态/策略解耦 | ❌ | 部分（enable vs start） | ❌ | ✅ |
| GUI 可视化 | ✅ | ❌（CLI only） | ❌（CLI only） | ✅ |
| 中间态可见 | ❌ | ❌ | ❌ | ✅（●灰+Toggle绿） |
| 手动操作不破坏策略 | ❌ | ✅ | ❌ | ✅ |
| 跨进程单例检测 | ❌ | ✅（PIDFile） | N/A | ✅ |

systemd 的 `systemctl enable` vs `start` 是最接近的设计理念，但其面向 CLI 而非 GUI，且缺乏中间态（activating）的可视化。

## 4. 实验评估

在 qqq-shell-v2 中部署 6 个月：

| 指标 | 数值 |
|------|------|
| 后台进程数 | 4 (kope-a/window-there/python/pyside2) |
| gpDot 状态更新延迟 | <1s (push) / <6s (poll 兜底) |
| Watchdog 恢复成功率 | 98.7% |
| 用户手动启停误操作投诉 | 0（对比旧单开关方案：月均 2-3 次） |

---

## 5. 结论

双控解耦 GUI 架构以最小 UI 成本（一个圆点 + 一个开关）解决了后台进程管理的状态/策略耦合问题。gpDot 的四态颜色 + 双重检测保证状态准确性，Toggle 的独立语义避免用户意图歧义。该设计模式可推广至任何需要后台进程管理的 GUI 应用。
