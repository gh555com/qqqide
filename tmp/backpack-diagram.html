🔍 当前拆解面板的三个致命错误

❌ 现在

  • Tool Results 121k
  • User × N 估算值
  • Compressed Summary 估算值
  • Permanent System 估算值
  • Completion (all AI) 125k ← 异类！不属于背包
  • Available 算错
问题 1：Completion 是输出，不该在背包面板。
问题 2：assistant.tool_calls JSON（几十KB）完全不计入任何行。
问题 3：可用空间 = 总量 - 用户估算 - Completion ← 单位混乱。

✅ 应该

  • 📋 Permanent System 精确 chars/3
  • 📦 Compressed Summary 精确 chars/3
  • 👤 User messages 精确 chars/3
  • 🤖 AI text (content) 精确 chars/3
  • 🔩 AI tool_calls JSON 精确 chars/3 ← 大事！
  • 🔧 Tool Results 精确 chars/3
  • ❌ Error messages 精确 chars/3
  • 📏 本地估算总和 ~xxxk
  • ⏱️ API 精确值 (prompt_tokens) ← 唯一真理秤
  • 📐 剩余 (总量 − 真理秤) ~xxxk
原则：本地估算是辅助拆解，API prompt_tokens 是唯一权威。
Completion 完全不在背包里，移到计费面板单独展示。

⚖️ 背包的真正天平 — API 精确值

背包重量 = API prompt_tokens

（每一间 house 的 SSE 流末尾都有一个 usage 事件，含 prompt_tokens）

可用空间 = 1,048,565 − prompt_tokens

❌ Completion 125k 跟背包无关！
Completion 是模型输出，是水龙头流出来的水，不是水箱里的水。

🔥 压缩触发 — 当前 vs 正确

❌ 现在

_lastApiTotalTokens > 阈值
Total = prompt + completion
把输出也当成背包重量！
这导致过早触发压缩——Completion 125k 不在背包里却参与判断，多算了 125k 的背包重量。

✅ 正确

_lastApiPromptTokens > 阈值
Prompt = 纯输入
压缩阈值用 prompt_tokens 而不是 total_tokens。Completion 是输出，不影响背包容量判断。

📝 小总结

💡三件事需要修正
A. 拆解面板去掉 Completion 行。 Completion 是输出，放计费面板。背包面板只展示实际塞进 messages[] 的内容。
B. 拆解面板加 assistant.tool_calls JSON 行。 这是背包里最大最隐蔽的格子。遍历所有 role='assistant' 消息，累加 tool_calls 的 JSON.stringify 长度。
C. 压缩阈值用 prompt_tokens 而不是 total_tokens。 agent-loop.js 第 491 行：_lastApiTotalTokens || _lastApiPromptTokens → 改为只用 _lastApiPromptTokens。和 agent-context.js 第 100 行的 _readCompressThreshold 调用方一起改。
背包真理源：API 返回的 usage.prompt_tokens（不含 completion）。本地拆解面板的各行只是辅助解释——用于帮你理解哪些格子占了最多空间。压缩只看真理源。
